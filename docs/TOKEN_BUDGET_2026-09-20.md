# Token & call budget — what the 2026-09-20 skills runs cost, and how the plugin cuts it

Source: `evals/runs/2026-09-20_skills.md` (S1 754 s / 78 calls, S2 715 s / 96 calls, S3 1269 active s / 150 calls;
193k–331k input tokens each). Tool-result bytes per session, by origin:

| origin | S1 | S2 | S3 | note |
|---|---|---|---|---|
| host profile skills (`known-errors`, `hermes-agent`, `tdd`) | ~71k | ~67k | ~67k | **real-world condition, not noise** — see §G: the profile's SOUL forces them, and they collide with the framework |
| reading the framework (README, two SKILL.md, LESSONS, `verification.py`, VERIFICATION.md, `install.py`, `check.py`) | ~60k | ~85k | ~55k | agents read **source** to learn what doctor/finish demand |
| project templates (USE_CASES 9k, AGENTS 8k, RELEASE/ARCHITECTURE 3k …) | ~30k | ~25k | ~25k | prose that teaches humans |
| rituals: package `verify.py` (12k), dry-run+install (8k), plant-a-fake-defect audits (16–25k), verbose unittest (8k), failed hub install (8k) | ~40k | ~45k | ~50k | zero project value |
| real work (code, tests, doc edits) | ~25k | ~35k | ~90k | |

First `write_file` happened at assistant turn 11 (S1), 18 (S2), 5 (S3). Early bytes are the expensive ones:
every later API call carries them again.

## Principle
The agent should never *read to learn the framework*; it should *call a tool that already knows it*.
Documents stay for humans and for the agent's project knowledge; the framework's own rules move into
tool descriptions (≤ 400 tokens each) and short command outputs (≤ 30 lines by default, `--full` on request).

## A. Remove the fixed start-up cost (≈ 60–85k bytes → ≈ 6k)
1. **`contract`** — one command/tool printing what doctor/finish/commit-check require, in ≤ 60 lines: required
   files, the UC heading/Test-field grammar, project.json keys, test-evidence rule, what "READY" and
   "PASSED" mean. Replaces reading `verification.py` (15k), VERIFICATION.md (7k), `check.py`, `install.py`.
2. **Tool descriptions carry the skill.** `init`, `catchup`, `check`, `brief` describe in their schema what to do and
   in what order; SKILL.md files inside the plugin shrink to < 3k and point to `help <topic>` for detail.
   LESSONS.md becomes `help lessons` — read when the agent wants the *why*, not on every install.
3. **Single-shot init.** `init(target, name, scale, profile)` = dry-run + install + summary in one call, ≤ 10 lines
   out. Scale accepts free text with a leading integer ("1 user (personal tool)" must not fail).
4. **No package self-test on the agent path.** `verify.py` is for framework contributors; the plugin is installed
   through `hermes plugins validate` — trust is decided there, not by re-running 93 tests.

## B. Replace rituals with commands (≈ 40–50k bytes, 8–12 calls → 3 calls, ≈ 1k)
5. **`check selftest`** plants the fake UC / secret / timer *in a temp copy* and reports three PASS/FAIL lines.
   Today catch-up tells the agent to plant them by hand in the real tree and restore (S2: 3 terminal calls, 24k,
   git noise, restore risk).
6. **Quiet test output.** `finish` prints counts + first failure; the full log goes to
   `.devframework/last_test.log` (already outside the tree — just stop echoing it).
7. **Installation is `hermes plugins install` + `enable`** — no git clone, no skills-guard (which blocks any
   skill that mentions `AGENTS.md`: rule `agent_config_mod`, verdict DANGEROUS, `--force` refused).

## C. Make every later session cheap — the real goal (agent reads context, does not rebuild it)
8. **`brief`** — ≤ 1.5k tokens: PROJECT facts, doctor state, git status/last commits, active checklist with open
   items, open KEs, UC count + untested UCs, last handoff. One read instead of 8 documents. Plugin hook
   `on_session_start` injects it automatically when cwd contains `.devframework/` → **zero calls**.
9. **`find <id|keyword>`** — returns the UC/KE/FR *block*, not the file (USE_CASES is 9k and grows). Structure-aware
   grep over stable ids the doctor already parses.
10. **`INDEX.md`** regenerated by `finish`: one line per UC/KE/FR/module → file/test. Always fresh, 1–2k, the thing a
    new session greps first. (Same idea as codemaps, but produced by the gate, so it cannot drift.)
11. **Checklists as a tool, not a file the agent re-reads and re-patches.** `checklist new|add|tick|show`; state in
    `docs/CHECKLIST_<slug>.md` as today. `show` prints only open items. Drop the rule "copy the checklist at the end
    of every reply" for agents (output tokens every turn); keep it as an operator-facing option.
12. **`handoff`** writes the handoff block from git log + checklist + doctor at session end (`on_session_end` hook
    reminds if a checklist has open items and no handoff was written). Next session's `brief` is then accurate.
13. **`uc new`, `ke new`** emit a correctly formatted block from fields → agent never reads the 9k template
    to learn the format; the template prose moves to `docs/GUIDE.md` (human-facing).

## D. Document design
14. **Agent-facing vs human-facing.** Catalogue files hold data with stable anchors
    (`<!-- df:uc-table -->`); explanations live in GUIDE.md. Doctor keeps parsing the same headings.
15. **Lite profile** for small/novice projects: PROJECT.md + USE_CASES.md + KNOWN_ERRORS.md + BACKLOG.md; the other
    five documents are "N/A until needed" and doctor does not demand them. Every extra document is one write now and a
    read in every future session. The core value (use case ↔ module ↔ test) needs exactly these four.
16. **AGENTS.md template shorter for lite**: no mandatory parallel subagents, no per-reply checklist copy; ceremony
    scales with profile.

## E. Output hygiene rules for every plugin tool
17. Default ≤ 30 lines / 2k chars; `--full` for more. Never echo a file the agent could `find`.
18. Errors are one structured line each with the fix (`SCALE must start with an integer, e.g. "100 users"`).
19. Accept `D:/x`, `D:\x` and `/d/x` alike (S3 lost two turns to git-bash paths).

## F. Model-side
20. Clarifications: allow up to 3 independent questions in one `clarify` call; sequential only when dependent.
21. Measure in **both** a fresh profile and a loaded one (e.g. the owner's engineering profile). The delta is the interference cost, a first-class KPI; `measure.py` reports foreign-skill bytes and lists which foreign skills were loaded.

## G. Coexistence with the host profile (found in the 2026-09-20 runs; sterile profiles are the exception)
What actually happened in a loaded profile (`mastermind`: SOUL + ~60 skills + verify-on-stop):

| mechanism | evidence | consequence | framework-side fix |
|---|---|---|---|
| **SOUL orders a skill read before any coding** ("read `known-errors` first") | 46k skill loaded at turn 1 in all three sessions; content is another product's defect list | irrelevant 46k in every later call; risk of cross-contaminating the project's own `KNOWN_ERRORS.md` (name collision) | the framework never fights SOUL — it must be cheap enough to *add* to it. Distinct names: tools/skills prefixed `df-`; no skill called `catch-up` or `known-errors` in a user's catalogue |
| **Hermes verify-on-stop** (`agent/verification_stop.py`, on by default) demands fresh verification evidence after code edits; evidence = commands from `project_facts.verifyCommands` (`scripts/run_tests.sh`, `package.json` scripts, `pytest.ini`/`[tool.pytest]`, Makefile targets) or a temp script named `hermes-verify-*` | a framework project has **none** of those markers → `check.py finish` is invisible → every session got the nudge and wrote 2 throw-away scripts *after* the final report (~10–15 calls each) | installer writes `scripts/run_tests.sh` → `python .devframework/check.py finish` (the convention Hermes already detects; it runs git-bash on Windows anyway). Then `finish` **is** the evidence and the nudge never fires. Upstream feature request: let the project context file declare verify commands |
| **Context-file precedence**: Hermes injects `.hermes.md`/`HERMES.md` (walk to git root) **else** `AGENTS.md` (**cwd only**) else `CLAUDE.md`; SOUL always; each capped (~20k default) and scanned for promptware | in the evals cwd was the profile home → our AGENTS.md was *not* injected (agents read it by hand, 8k). In real use it is injected every turn, stacked on SOUL | ship a small `.hermes.md` (found from any subdirectory) carrying only: precedence note ("SOUL wins on tone/format; this file wins on project gates"), the gate commands, where the docs are. ≤ 1.5k. AGENTS.md stays for other agents but shrinks too; both must pass the promptware scanner |
| **Rule stacking**: SOUL "append a 🟢 block to every reply" + framework "copy the checklist at the end of every reply" + SOUL "RED test first" + framework test rules + profile `test-driven-development` skill | two mandatory footers per reply; an 11k TDD skill loaded on top of framework rules | framework rules are *facts and gates*, not behaviour sermons; no per-reply rituals; say explicitly "if your profile already prescribes a test discipline, keep it — the gate only checks evidence" |
| **Skills-guard** (`agent_config_mod`) blocks hub install of any skill mentioning `AGENTS.md` | all three runs fell back to manual copy | plugin distribution (`hermes plugins validate` is the gate, not skills-guard); bundled skills avoid the literal strings where possible ("the project context file") |

Eval protocol consequence: every scenario runs twice — fresh profile and loaded profile. The loaded-profile run is the
one that predicts real users. `measure.py` reports `foreign skills` (names + bytes).

## Expected effect (rough, to be measured with the same evals)
Tool-result bytes S2 ≈ 275k → ≈ 90k; calls 96 → ≈ 45; first productive action turn 18 → ≈ 3.
Follow-up sessions: `brief` via hook → first code edit within 3–5 calls.

## Not doing
MCP server, embeddings/RAG over docs, a TUI, JSON-source docs generated to Markdown, rewriting `check.py`.
Markdown with stable ids + small stdlib parsers is enough; the doctor already proves it.

## Order of work
1. `contract`, `brief`, `find`, `INDEX.md` (pure stdlib scripts in `.devframework/`, usable without the plugin too).
2. `check selftest`, quiet `finish`, single-shot `init`, free-text scale.
3. Lite profile + GUIDE.md split + shorter AGENTS template.
4. `checklist`, `handoff`, `uc new`/`ke new`.
5. Plugin wrapper: tools + hooks + bundled skills; then re-run evals S1–S3 + FOLLOWUP in fresh profiles.
